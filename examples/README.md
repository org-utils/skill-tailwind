# Examples — components in both approaches (A · utilities, B · BEM+`@apply`)

Ready-to-use, framework-agnostic component examples for **Tailwind CSS v4 (CSS-first)**: pure
HTML + CSS/SCSS, no Vue/React/Nuxt/Svelte, no JS dependencies (the only JS is native
platform calls on `<dialog>`/`<details>`/`<form method="dialog">`, not a framework). Where
a component needs stateful JS for full WAI-ARIA semantics (`tabs`: roving tabindex + Arrow/Home/End),
a framework is **not faked** — the limitation is flagged explicitly, and the JS is left as a marked TODO.

Each component is provided in **two equal** implementations of the same UI:

- **Approach A — utility-first** (`*.utility.html`): classes live right in the markup (co-location,
  thin bundle, no "stale" overrides). The starting rungs of the abstraction ladder (1–3).
- **Approach B — BEM + `@apply`** (`*.bem.html` + `*.bem.scss`): the markup carries semantic
  BEM classes, the look is composed from utilities via `@apply`, **grouped by property type**.
  A deliberate choice of the upper rungs of the ladder (4–6).

**Both are equally valid.** The choice is a matter of context (repeated markup, third-party/generated DOM,
team convention, "readable at a glance"), not "right/wrong". The methodical
breakdown and decision tree are in `references/approaches.md`; `@apply` grouping in `resources/apply-grouping.md`.

> **Premise for all files.** The examples assume the canonical `@theme` from
> `templates/theme.css` — semantic tokens (`bg-background`/`text-foreground`,
> `bg-card`/`text-card-foreground`, `bg-primary`/`text-primary-foreground`, `border-border`,
> `ring-ring`/`outline-ring`, `bg-danger`/`text-danger-foreground`, `rounded-sm/md/lg/xl` …).
> **Token names are stable; values are placeholders**, replaced to fit the project's design system.
> Dark mode works "for free": every color is a token that `.dark` overrides, so the
> markup needs no `dark:` variants of its own.

## How to use this

1. Wire up Tailwind v4 and the canonical `@theme` (see `templates/theme.css`, usually via
   `templates/entry.css`).
2. Pick an approach per component (decision tree — `references/approaches.md`):
   - **A** — take `*.utility.html` and paste the markup as is; change token classes to fit the look.
   - **B** — take `*.bem.html` (markup) **and** `*.bem.scss` (styles). If the SCSS is compiled
     **separately** from the entry CSS (CSS module / isolated `<style>` / framework scoped style),
     add `@reference "…";` as the first line pointing to your Tailwind entry; if the file is in the same build that
     already has `@import "tailwindcss"`, that line is **not needed** (a repeated reference is redundant).
3. Replace the token **values** to fit your design system; leave the **names** alone — all the
   examples rely on them. There is no need to hardcode hex/oklch in the markup.

> **A/B pairing.** For every component the utility version and the bem version render the **same** UI
> (same structure, same states) — this lets you diff the approaches on identical markup.

## Invariants (met in all examples)

- **Tailwind v4 only.** Slash opacity (`bg-primary/90`), `outline`/`ring` focus,
  `@starting-style`/`starting:`, container queries. No `@tailwind`/`bg-opacity-*`/
  `bg-gradient-to-*`/`bg-[--var]`/JS config.
- **Canonical semantic tokens only** by name; values are placeholders, no hardcoded hex/oklch in the markup.
- **Strict BEM, canonical default scheme** — element separator `-`, modifier separator `_`
  (camelCase, lowercase-first, for multi-word parts): block `cardList`, block modifier
  `cardList_compact`, element `cardList-item`, element modifier `cardList-item_active`, key/value
  modifier `cardList_size_lg`. One block per component, the modifier never stands alone
  (`block block_mod`), no elements-of-elements (`block-a-b`) chains. The scheme is configurable: if a
  project declares another convention, follow it — only the hard rules (programmatically separable,
  modifier never alone, no nested elements) always hold.
- **`@apply` grouping (approach B)**: layout → sizing → spacing → background/borders/shape →
  typography → effects/motion → interaction; then states, then modifiers — on a separate
  line with a comment.
- **Accessibility**: semantic markup (`button`/`label`/`dialog`/`nav`/`ul`), visible
  `focus-visible`, a full set of states on interactive components (a field — also `invalid`),
  correct `aria-*` and relationships (`label[for]`/`aria-describedby`/`aria-labelledby`), contrast via
  `*-foreground` pairs.
- **No AI-slop**: neutral "production-grade" skeletons, without purple-blue gradients,
  glassmorphism/`backdrop-blur`, `rounded-full` without reason and decorative blobs.

(skeleton inventory), `references/tokens.md` and `templates/theme.css` (`@theme`),
