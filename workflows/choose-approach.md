# Workflow: choosing approach A (utility-first) vs B (BEM + `@apply`)

> Step-by-step workflow: how to consciously choose, for a **specific** component/task, between approach A
> (utilities in the markup) and approach B (semantic BEM classes with grouped `@apply` in SCSS) —
> and immediately start in the chosen approach from a skeleton.
>
> **Both approaches are equal.** This is not a "right/wrong" choice but picking the right tool for the
> context: repeated markup, third-party/CMS DOM, team convention, number of states/variants, and the
> importance of "readability at a glance". Within **one project** it is normal to **combine** them: a button —
> via B, a one-off section — via A; see §4.
>
> This file is an executable playbook on top of the methodological reference `references/approaches.md`
> (which holds the philosophy, the pros, the abstraction ladder, the "good/bad `@apply`" rule, and the full
> tree in §5). Here we do **not** duplicate its tables; we guide you step by step and link out.

---

## Step 0. State the inputs

Pin down three facts about the component/task — every fork below relies on them:

- **Repetition:** does this UI appear once (one-off) or many times?
- **Control over the DOM:** do you own the markup, or is it generated by a third-party source (CMS, markdown
  renderer, third-party widget, DOM rewritten by a script)?
- **Repository convention:** has the project already adopted one of the approaches as a team standard?

Keep the canonical `@theme` (`templates/theme.css`) at hand: in both approaches the look is assembled from
**semantic tokens by name** (`bg-primary`/`text-primary-foreground`, `border-border`,
`ring-ring`/`outline-ring`, `rounded-md` …), with values as placeholders for the design system. Choosing A vs B
does **not** change the tokens — only *where the classes live* changes (in the markup or in `@apply`).

---

## Step 1. Third-party / generated DOM?

**Question:** do you control the markup, or is it served by an external source whose nodes you cannot extend
with utilities (CMS/markdown output, a third-party widget, DOM rewritten by a script)?

- **Third-party/generated DOM → approach B (`@apply` adapter).** There is nowhere to put utilities — you need a **real
  CSS class** on the selector that the source renders; `@apply` adapts the design tokens to it. This is
  rung 6 of the ladder and the canonical "good `@apply`" (see `references/approaches.md` §4).
  **→ go to Step 5 (skeleton B).**
- **You own the markup → continue to Step 2.**

> This is the first (and the "hardest") fork: with a third-party DOM the choice is effectively predetermined, and the rest of the
> questions are unnecessary.

---

## Step 2. A convention adopted in the repository?

**Question:** does the project already have an established approach (utilities in the markup everywhere / BEM
blocks with `@apply` everywhere)?

- **There is a convention → follow it.** Codebase consistency matters more than personal taste; a new component
  should not break from the adopted style. **→ skeleton of the corresponding approach (Step 4 or Step 5).**
- **No convention / this is greenfield → continue to Step 3.**

---

## Step 3. Markup repetition and state complexity

Now the fork is about the nature of the component. Go through it in order.

**3.1 Does the markup repeat?**

- **No (one-off, simple block) → approach A.** Compose utilities right in the markup: co-location, a thin
  bundle, no need to invent names. **→ Step 4.**
- **Yes → 3.2.**

**3.2 Is it the MARKUP that repeats — can it be extracted into a reusable fragment (partial / include /
template / component)?**

First separate the **two axes**, because they have **different** fixes:

- **MARKUP reuse** (the same HTML appears on many pages — a header, a footer, a nav) → solved by a
  **template/partial/include**, *not* by CSS.
- **CSS reuse** (the same *styling* recurs on differently-structured nodes, or on DOM you don't own) → that is
  what BEM + `@apply` (approach B) addresses.

So:

- **Yes, the markup can be extracted → extract it, keep the styles utility-first (approach A).** This is **rung 2**
  of the ladder: the duplicate goes away **without** a CSS abstraction. Don't hide utilities behind a semantic
  class just for shorter markup — that is "bad `@apply`" (`references/approaches.md` §4). **→ Step 4.**
- **The identical markup repeats but there is no partial/include/component mechanism (plain static HTML) → still
  an A problem, see Step 3.2a.** Markup duplication is a *markup* axis; do **not** route it to approach B —
  `@apply` deduplicates CSS, not HTML.
- **It is the STYLING that recurs, on nodes you can't share as one fragment (the same look on differently-structured
  blocks, or on third-party / generated DOM) → that's the CSS axis → 3.3.**

**3.2a Partial-less static HTML — how to handle duplicated markup**

When the toolchain has **no** partial/include mechanism (hand-written multi-page static HTML), there is no
rung-2 extraction point. Resolve the *markup* axis, in order of preference — and keep the styling utility-first:

1. **Add a build-time include step (preferred — the real rung-2 answer).** Any static-HTML include/partial step
   (a small build that stitches shared fragments, e.g. via the Tailwind CLI alongside a templating/include step,
   PostCSS-driven includes, or any HTML-include build plugin) lets one `header.html` / `footer.html` be the
   single source of the shared markup. Then it is ordinary approach A.
2. **If you accept the duplication, keep the per-page difference to a SINGLE source of truth.** Don't hand-edit
   the active nav item (and its `aria-current`) in every file. Put **one** flag on a stable ancestor —
   `<body data-page="play">` — and drive the active state from it with a v4 data-attribute variant
   (`data-[…]:…`), so only one attribute changes per page:

   ```html
   <body class="group/page" data-page="play">
     <!-- … duplicated header markup, identical on every page … -->
     <a href="/play"
        class="px-3 h-9 inline-flex items-center rounded-md text-muted-foreground
               group-data-[page=play]/page:bg-accent group-data-[page=play]/page:text-accent-foreground">
       Play
     </a>
   ```

   The descendant reads the ancestor's flag through the named group `group/page` (the v4 `group-data-[…]:`
   variant); only the one `data-page` value differs between files. Add the matching `aria-current="page"` the
   same way — derived from the one flag, not retyped per file. This still leaves the HTML duplicated, so prefer
   option 1 when a build step is available.

**Either way the styling stays utilities-in-markup (approach A); BEM + `@apply` does not solve markup
duplication. → Step 4.**

**3.3 Many intent variants + states, and is "readability of the markup at a glance" important?**

- **Moderate (1–2 states, no proliferation of variants) → approach A** with variant prefixes
  (`hover:` / `focus-visible:` / `active:` / `disabled:`) copes. **→ Step 4.**
- **Many variants/states and readability is critical → approach B.** A semantic block: a **neutral
  base**, while tone/intent and states go into modifiers and nested `&:hover/&:focus-visible/...`.
  **→ Step 5.**

> The full tree with the rationale for each leaf is in `references/approaches.md` §5 (and a short version in
> `SKILL.md` → "Decision trees"). Here is the same route, presented step by step.

---

## Step 4. Start in approach A (utility-first) — skeleton

Compose from semantic tokens right in the markup. The base layout is mobile-first (unprefixed
utilities = all screens, `md:` *adds* changes upward). For interactives a **full set of
states** hover / focus-visible / active / disabled is mandatory.

```html
<button type="button"
  class="inline-flex items-center justify-center gap-2
         h-10 px-4
         rounded-md bg-primary
         text-sm font-medium text-primary-foreground
         transition-colors duration-150
         hover:bg-primary/90
         focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-ring
         active:bg-primary/80
         disabled:opacity-50 disabled:pointer-events-none">
  Continue
</button>
```

Next:

1. Swap the token classes for the look you need (`bg-primary` → `bg-card`, etc.) — the token **names** come from
   `templates/theme.css`, the values are already set by the theme; don't hardcode hex/oklch in the markup.
2. If the markup starts to repeat — extract it into a partial/fragment (rung 2), staying in A.
3. Take ready-made A references from `examples/<name>/<name>.utility.html` (`button`, `card`, `badge`,
   `alert`, `navbar`, `modal`, `input-field`, `responsive-grid`).

---

## Step 5. Start in approach B (BEM + `@apply`) — skeleton

The markup carries **semantic BEM classes**; the look is assembled from utilities via `@apply`, **grouped
by property type**. Default BEM (element `-`, modifier `_`, mod-value `_`, camelCase lowercase-first for
multi-word parts — and follow the project's scheme if it declares another): block `cardList`, block modifier
`cardList_compact`, element `cardList-item`, element modifier `cardList-item_active`. One block per
component, elements always derive from the block, no `-a-b` chains.

Markup:

```html
<button type="button" class="button button_primary">
  <span class="button-icon"><svg aria-hidden="true"><!-- icon --></svg></span>
  Continue
</button>
```

SCSS (group order: layout → sizing → spacing → background/borders/shape → typography → effects →
interaction; then states; then modifiers — each group on its own line):

```scss
@reference "tailwindcss"; /* needed ONLY if the SCSS is compiled separately from an entry with @import "tailwindcss" */

.button {
  @apply inline-flex items-center justify-center gap-2;
  @apply h-10;
  @apply px-4;
  @apply rounded-md border border-transparent; /* neutral base */
  @apply text-sm font-medium;
  @apply transition-colors duration-150;
  @apply cursor-pointer select-none;

  &:focus-visible { @apply outline-2 outline-offset-2 outline-ring; }
  &:disabled      { @apply opacity-50 pointer-events-none; }

  &-icon {                                   /* element */
    @apply inline-flex items-center justify-center;
    @apply size-4 shrink-0;
  }

  &_primary {                                /* modifier: tone separate from the base */
    @apply bg-primary;
    @apply text-primary-foreground;
    &:hover  { @apply bg-primary/90; }       /* slash opacity — v4 */
    &:active { @apply bg-primary/80; }
  }
}
```

Next:

1. `@reference` is needed **only** when the SCSS is built separately (CSS module / isolated/scoped
   `<style>`); in a shared build with `@import "tailwindcss"` the line is **redundant** — delete it.
2. Keep the base **neutral** (layout/spacing/shared), put color/intent into modifiers: that way exceptions don't
   "fight" the base.
3. See the grouping and a worked example in `resources/apply-grouping.md` and `resources/property-order.md`;
   ready-made B references are `examples/<name>/<name>.bem.html` + `examples/<name>/<name>.bem.scss`.

## Worked mini-cases

### Case 1. A reusable button (4 variants × 3 sizes + states)

- Step 1: DOM is yours. Step 2: no convention. Step 3.1: it repeats. Step 3.2: extraction is possible, **but** Step 3.3 —
  many intent variants (`primary`/`outline`/`ghost`/`danger`) × sizes (`sm`/`md`/`lg`) + a full
  set of states, markup readability is critical.
- **Decision: approach B.** Neutral base + tone/size in modifiers (`button_primary`, `button_sm`),
  element `button-icon`. Reference — `examples/button/button.bem.html` + `examples/button/button.bem.scss`.
- *Note on combining:* even after choosing B for the button, a landing section can be assembled from it utility-first
  (Case 2) — the approaches coexist within one project.

### Case 2. A one-off landing section (hero / CTA)

- Step 1: DOM is yours. Step 2: no convention. Step 3.1: it does **not** repeat (a unique one-off block).
- **Decision: approach A.** Utilities right in the markup: co-location, no point inventing BEM names for a single
  block — that would be "bad `@apply`" (a semantic wrapper without reuse). Skeleton —
  Step 4; build the layout mobile-first (`flex-col … md:flex-row`). Ready-made A patterns —
  `examples/*/*.utility.html`.
- *One-off page layout stays in markup even on a B-leaning project.* Approach B is for **repeated named
  primitives** (button/card/badge/field). A non-reused page (hero, section grids, spec lists) wrapped in one
  block with 20+ single-use elements is just utility-soup relocated into SCSS — keep it utilities-in-markup.

### Case 3. Styling markdown / CMS output (`.prose`-like content)

- Step 1: the DOM is **third-party/generated** — the `<h2>`/`<p>`/`<a>` rendered from markdown/CMS have nowhere
  for utilities in the markup.
- **Decision: approach B (`@apply` adapter), right away from Step 1.** You create a real wrapper class and
  style the child nodes by the renderer's selector via grouped `@apply` — this is the canonical
  "good `@apply`" (`references/approaches.md` §4). Skeleton — Step 5; grouping —
  `resources/apply-grouping.md`.

---

## Final cheat sheet

1. Third-party/CMS DOM → **B** (adapter), the decision is made right away (Step 1).
2. Otherwise, if there is a team convention → **follow it** (Step 2).
3. Otherwise: one-off/simple, or **repeated MARKUP** → **A** (extract a partial/include — add a build-time
   include step if the toolchain has none; never `@apply`, which dedupes CSS, not HTML); **repeated STYLING on
   unshareable nodes** with many variants+states and readability matters → **B** (Step 3).
4. One-off **page** layout (hero/sections/grids) stays utilities-in-markup even on a B-leaning project; B is for
   repeated named primitives.
5. **A and B are equal and combine within one project** — choose by context, not by a hierarchy of value.
